# Releasing

The [0.1.0 scope](../release-0.1.0.md) and
[known limitations](../reference/known-limitations.md) describe what a release
promises. This runbook is the procedure for every release. Until 0.1.0 is
out, also work through the [first-release checklist](first-release.md).

The workspace publishes five crates in lockstep, in this dependency order:
`excalidraw-render-fonts-xiaolai`, `excalidraw-render-fonts-xiaolai-extended`,
`excalidraw-render-fonts`, `excalidraw-render`, `excalidraw-render-cli`. The font
crates carry the Excalidraw release as build metadata
(`0.1.0+excalidraw.0.18.1`). crates.io ignores build metadata when comparing
versions, so a font refresh for a new Excalidraw release needs a new version
number, not only new metadata.

## Versioning rule for output bytes

A patch release never moves the golden record (`tests/conformance/golden`)
or a parity pin: it carries fixes whose artifact bytes are unchanged for every
registered export target, so an application that pinned the previous patch
sees the same bytes. A change that moves them, including a bump of a crate in
Dependabot's `output-bytes` group (Krilla, HarfRust, usvg, resvg, tiny-skia,
skera, the decoders, …), waits for the next minor release, and the minor
release restages everything it moved once: `just update-golden`, the
two-sided tolerance exceptions the parity harnesses report, and the
representative candidate through `restage.yaml`. The golden test classifies
the change; the review of its diff is the acceptance.

## 1. Prepare the candidate

The release tooling is in the `maintainer` devenv profile
(`devenv --profile maintainer shell`): cargo-release bumps, tags and publishes,
and dist (`dist plan`, `dist generate`) owns the binary release workflow.

1. Bump every crate in lockstep and commit the bump as `release X.Y.Z`:

   ```sh
   cargo release X.Y.Z --no-publish --no-tag --no-push --execute
   ```

   cargo-release moves `version` in `[workspace.package]`, every font crate's
   `version` (keeping its `+excalidraw.X.Y.Z` metadata), the `=X.Y.Z`
   requirements in `[workspace.dependencies]`, and `Cargo.lock`. It runs only
   on `main`; on a release branch for a pull request, add
   `--allow-branch <branch>`.
2. Make sure the tree is clean: release provenance must not come from an
   edited working tree. Land the commit on `main`.

## 2. Verify

In the devenv shell, on any supported host (the release checks need the
`release` profile: `devenv --profile release shell`). The `Release checks`
workflow runs `just release` from the release commit; the others run locally
or come from the commit's CI run:

```sh
just ci
devenv --option languages.rust.version:string 1.92.0 shell -- just msrv
devenv --profile release shell -- just release
cargo publish --workspace --dry-run --locked
dist plan --tag vX.Y.Z
```

`just ci` is the per-change gate (lint, tests, conformance, packaging),
`just msrv` the MSRV check, and `just release` the release checks: the
release-tier verifiers and tests, native and experimental-WASM qualification,
the packaged consumers in WASM and the golden targets in WASM. The PDF and SVG
viewer harnesses run nightly and on demand (`just pdf-harness`,
`just svg-harness`); see [conformance operations](../../tests/conformance/README.md).
The publish dry run packages and compiles every crate against its packaged
dependencies, and `dist plan` lists the archives and installer the tag will
produce.

## 3. Tag and publish

From the verified commit on `main`:

```sh
cargo release --execute
```

With no version argument cargo-release releases the version already in the
manifests: it publishes the five crates in dependency order, waiting for each
to reach the index before publishing its dependents, then creates the signed
`vX.Y.Z` tag and pushes it with `main`. If publishing stops part way, publish
the remaining crates in order with `cargo publish -p <crate>`, then tag and
push with `cargo release tag --execute` and `cargo release push --execute`.

The tag starts the `Release` workflow (`release.yml`, generated by dist): it
builds the `excalidraw-render` archives for Linux (x86-64 and ARM64, glibc and
musl) and macOS (x86-64 and ARM64) with the toolchain `rust-toolchain.toml`
pins, each with a SHA-256 file, plus a shell installer, and creates the GitHub
release with them. Only Linux x86-64 (glibc) is release-qualified. Once the
release is out, the workflow builds the side-by-side demo from the tag and
deploys it to GitHub Pages (`pages.yml`).

Check that [docs.rs](https://docs.rs/crate/excalidraw-render/latest/builds)
built `excalidraw-render`.

## 4. Write the release notes

dist writes the release body: install instructions and the artifact table.
Add a summary of the release above it with `gh release edit vX.Y.Z`; link
repository files by full URL and carry no placeholder text.
`gh api repos/{owner}/{repo}/releases/generate-notes -f tag_name=vX.Y.Z`
lists the merged pull requests since the previous tag.

## 5. Smoke-test the published artifacts

```sh
cargo install --locked excalidraw-render-cli --version X.Y.Z
excalidraw-render tests/conformance/cases/focused/bound-text-containers/scene.excalidraw -o /tmp/smoke.svg
```

Also install through the shell installer on the release page, or unpack the
Linux x86-64 archive and verify its checksum, and run
`excalidraw-render --version`, which prints
`excalidraw-render X.Y.Z (Excalidraw 0.18.1)`. Check that the demo on GitHub
Pages names the release commit. Then add the release commit, crate checksums,
and the release-check logs to the GitHub release notes (`gh release edit`):
the tag is already fixed.
