# Font subsetting module ecosystem

Primary-source survey checked 2026-07-31. This report asks which maintained modules can supply either a general font-subsetting/WOFF2 layer or reusable SVG-font integration for a pure-Rust renderer. It complements, rather than repeats, [`font-subsetting-primary-sources.md`](font-subsetting-primary-sources.md), which already fixes the Excalidraw behavior, licensing questions, resource-accounting design, local four-codepoint spike, and all-230-font verification gates.

## Conclusion

Package reuse is appropriate only for the three narrow font transformations: reuse and qualify exactly pinned `wuff 0.2.8`, `skera 0.5.1`, and `ttf2woff2 0.13.2`, using an adapter first and a controlled fork where qualification fails. Use HarfBuzz and fontTools as external differential oracles. No surveyed reusable package supplies the renderer's SVG semantic integration: none both derives the required semantic font demand and emits the governed subset `@font-face` bundle. The approved draft-revision-1 architecture is therefore:

1. **Keep `wuff 0.2.8` as the WOFF2-to-sfnt decoder.** It is already in this workspace, is pure Rust and `no_std`, imposes a table-derived Brotli output bound and compression-ratio check, and has locally decoded all 230 sealed official assets. Its API is decode-only, so it does not decide subset policy. [Source: `wuff` manifest and API](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/Cargo.toml#L1-L41), [pre-decompression bounds](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/decompress_woff2.rs#L21-L100), [existing 230-font result](font-subsetting-primary-sources.md#candidate-assessment)
2. **Qualify exactly pinned `skera 0.5.1` as the subset implementation, but admit it only through a narrow adapter or controlled fork.** It has the best pure-Rust web-font scope and active upstream work, but it is new, has reachable malformed-font panics, omits MATH closure and CFF/CFF2 table dispatch, has unfinished paths, and is not itself exercised by fontations' `wasm32-unknown-unknown` CI job. [Source: crate history](https://crates.io/api/v1/crates/skera), [closure and panic sites](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L555-L614), [table dispatch](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1243-L1387), [fontations WASM job](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/.github/workflows/rust.yml#L176-L200)
3. **Qualify exactly pinned `ttf2woff2 0.13.2`, with default features disabled, as the sfnt-to-WOFF2 encoder.** Its single-thread path is explicitly deterministic and its WASM path is explicitly single-threaded, but it accepts only TrueType-flavored sfnt and performs infallible internal allocations without renderer resource hooks. Those limits happen to match the sealed 230-font corpus, not arbitrary caller fonts. [Source: manifest](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/Cargo.toml#L1-L33), [determinism and WASM behavior](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L20-L59), [accepted flavor and allocation](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/sfnt.rs#L8-L65)
4. **Do not add an SVG-font integration dependency.** The renderer must own scene-text collection, family/chunk selection, fallback and declaration order, subset-profile constants, CSS/data-URL serialization, licensing names/notices, validation, failure policy, caching semantics, and resource transactions. `usvg` is useful for parsing/rendering external SVG and can expose text chunks and font properties, but it neither subsets fonts nor writes `@font-face`; using it as the primary exporter would also violate this repository's prohibition on a serialized-SVG pivot. [Source: `usvg` text model](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/tree/text.rs#L115-L178), [text chunks and spans](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/tree/text.rs#L319-L576), [writer behavior](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/writer.rs#L17-L125), [current typed-plan rule](../renderer-spec-v1.md#9-architecture)

This is a reuse recommendation, not production admission. Revision 1 is unpublished and draft; the approved amendment now includes direct scene/frame SVG subsetting, and first publication is its immutability boundary. The pre-amendment draft at commit `9d6ce4f16b3c3a67d5e88f472519a1ad91af4978` forbade runtime subsetting, but that is a superseded historical constraint rather than current policy. Implementation and qualification still require the safety, all-font, native/WASM, typography, licensing, deterministic-byte/resource-trace, size, dependency, performance, footprint, and release-evidence gates. [Source: historical draft dependency and asset contract](https://github.com/sagikazarmark/excalidraw-render.orig/blob/9d6ce4f16b3c3a67d5e88f472519a1ad91af4978/docs/renderer-spec-v1.md#L794-L826), [current draft boundary](../renderer-spec-v1.md#3-compatibility-identity), [approved subsetting contract](../renderer-spec-v1.md#83-typography), [companion verification gates](font-subsetting-primary-sources.md#verification-gates)

The implementation boundary is two package-private deep modules plus a thin Excalidraw adapter. `font_subset` exposes a qualified-chunk-only request-scoped session interface and owns decode/plan/sfnt/encode/validation plus that inner resource transcript. `svg_fonts` accepts typed semantic SVG font demand, never serialized SVG, and returns a typed opaque bundle with matching measure/write operations; it owns family/range selection, CSS/data-URL/bundle work, and that outer transcript. The adapter owns normalized `originalText`, emitted generated labels, resolved source families, omission/recovery, and CJK copied-set behavior. Dependencies are strictly adapter to `svg_fonts` to `font_subset`, and both modules remain in the renderer until a concrete extraction need exists. [Source: approved architecture](../renderer-spec-v1.md#9-architecture), [domain terms](../../CONTEXT.md#language)

## Evaluation boundary

The repository accepts a production dependency only if it runs natively and on `wasm32-unknown-unknown` without production JavaScript, browser/OS services, system packages, network access, or host fonts; preserves artifact bytes; is bounded and panic-free on the renderer-controlled surface; and has acceptable licensing and provenance. First-party code forbids unsafe, build scripts are denied by default, and rendering/serialization dependencies and all transitive versions are release-gated. [Source: current dependency and release gates](../renderer-spec-v1.md#10-dependencies-assets-and-distribution)

The target here is narrower than arbitrary-font service software: the revision-1 implementation operates only on digest-verified, qualified official assets. Nevertheless, malformed-input and allocation behavior still matters because WOFF2 decode, generated sfnt handling, and output validation are parser surfaces, and the repository's gate explicitly requires no panic, trap, unbounded allocation, complete-chunk fallback, or partial artifact on native or WASM. [Source: approved qualified-built-in boundary](../renderer-spec-v1.md#831-semantic-demand-and-face-selection), [existing safety gate](font-subsetting-primary-sources.md#verification-gates)

WOFF2 is packaging, not subsetting. It can represent the entirety of TrueType/OpenType, including variable and color fonts, and its reconstruction rules permit functionally identical sfnt bytes that are not bitwise identical. An encoder/decoder therefore cannot supply glyph/layout closure policy, and exact bytes must be frozen per chosen implementation rather than compared across encoders. [Source: WOFF2 status and scope](https://www.w3.org/TR/2024/REC-WOFF2-20240808/#abstract), [reconstruction variability](https://www.w3.org/TR/2024/REC-WOFF2-20240808/#table_dir_format)

## Pure-Rust candidates

### `skera 0.5.1`

**Interface and actual scope.** `Plan::new` accepts glyph and Unicode sets, flags, table-drop policy, layout scripts/features, name IDs, and name languages; `subset_font` walks the source table directory and builds a new sfnt. The plan starts from `.notdef`, performs cmap and bidi closure, GSUB/GPOS closure, COLR closure, variation-selector handling, and recursive TrueType composite closure. MATH closure is explicitly skipped. [Source: plan inputs](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L395-L438), [Unicode and layout closure](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L441-L614), [public subset operation](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1133-L1155)

The implementation handles cmap, BASE, bitmap strikes, COLR/CPAL, GDEF/GSUB/GPOS, `glyf`/metrics, `gvar`, HVAR/VVAR, names, OS/2, `post`, `sbix`, VORG, and selected pass-through variation tables. Unknown tables are dropped unless the caller requests pass-through. The dispatch has no CFF or CFF2 arm, so current generality is narrower than “all OpenType”: CFF tables fall into the unknown-table behavior. [Source: table dispatch](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1243-L1387)

**Names and variations.** Name IDs/languages are first-class plan inputs. `gvar`, HVAR and VVAR are subset; `fvar`, `cvar`, `avar`, MVAR and STAT are passed through rather than axis-instanced. CFF desubroutinization, legacy-name retention, and IUP delta optimization flags are explicitly unimplemented. A renderer profile must therefore set every relevant option explicitly and must not infer full variable-font instancing or complete name preservation. [Source: flags](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L225-L271), [variation dispatch](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1298-L1343)

**sfnt/WOFF2 and web suitability.** Input and output are sfnt; there is no WOFF or WOFF2 codec. Its layout, cmap, metric, name, color, and variation-table scope makes it the only surveyed pure-Rust subsetter plausibly intended for standalone/web fonts rather than PDF embedding. It still requires `wuff` before and `ttf2woff2` after. [Source: public API and builder](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1133-L1155), [crate description](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/README.md)

**Determinism, safety, and resources.** The code uses ordered integer sets and stable FNV maps, but upstream documents no byte-stability contract. More importantly, planning calls `expect` for required `maxp` and `glyf` data and has other invariant `unwrap`s, while table serialization recursively doubles an infallibly allocated buffer up to a source-table-derived `256x` threshold. That is not the repository's checked, pre-reserved semantic resource ledger and is not panic-free for arbitrary fonts. [Source: reachable expectations](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L555-L593), [maxp expectation](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L967-L975), [serializer growth](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/src/lib.rs#L1174-L1233)

The crate has empty default features, no package build script, and pure-Rust direct dependencies; the inspected crate source contains no `unsafe` block. Its `skrifa`, `read-fonts`, `write-fonts`, and scalar-type foundations are built for `wasm32-unknown-unknown` in upstream CI, but the WASM job does not build `skera` itself. Native tests also install Python reference requirements, which are test-only and not runtime dependencies. [Source: manifest](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/skera/Cargo.toml#L19-L42), [native tests](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/.github/workflows/rust.yml#L102-L118), [WASM job](https://github.com/googlefonts/fontations/blob/734d3e01b1b5ad2e8e5a6fc3226ba8dbe4861830/.github/workflows/rust.yml#L176-L200)

**Arbitrary inputs and fit.** Upstream accepts general `FontRef` input, but current panic and format gaps mean arbitrary caller fonts cannot be admitted to the renderer-controlled surface. For this repository, the relevant narrower question is whether a frozen profile succeeds on every selected-codepoint class across all 230 known TrueType-flavored assets with identical native/WASM bytes and no panic under malformed generated/intermediate data. Until that qualification passes, `skera` is a source candidate, not an approved dependency.

### `wuff 0.2.8`

**Interface and directions.** The crate exposes WOFF1 and WOFF2 decode functions, including custom zlib/Brotli callbacks, and returns reconstructed sfnt bytes. It performs no glyph selection, layout closure, name/table filtering, variation instancing, or WOFF2 encoding. [Source: public exports](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/lib.rs#L1-L31)

**Web-font and format support.** WOFF2 decoding reconstructs collections and transformed `glyf`/`loca`/`hmtx`, copies untransformed tables, recalculates checksums, and sorts tables as required by WOFF2. This is exactly the decode half needed before sfnt subsetting, but it cannot establish that the resulting subset remains a valid web font. [Source: decode flow](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/decompress_woff2.rs#L38-L123), [table reconstruction](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/decompress_woff2.rs#L139-L354)

**Determinism, safety, and resources.** The crate is `no_std`, uses an `alloc`-backed pure-Rust Brotli decoder when enabled, has no build script, and the inspected source has no `unsafe` block. Before Brotli, it derives the exact decompressed block size from validated table entries, rejects ratios above 100, and requires exact decompressed length. That is unusually helpful bounded-allocation behavior. It still uses infallible `Vec` allocations and internal `expect`/`unwrap` invariants; enabling its `debug` feature intentionally converts parse errors into panics, so production must forbid that feature and still fuzz/validate the exact graph. [Source: manifest and features](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/Cargo.toml#L20-L41), [bounds](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/decompress_woff2.rs#L75-L106), [debug error behavior](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/error.rs#L30-L90)

The same fixed input and crate graph should decode deterministically, but upstream does not promise byte identity across versions or other decoders, and WOFF2 itself permits semantically equivalent reconstruction bytes. The crate is architecturally suitable for `wasm32-unknown-unknown` because it is `no_std` and its Brotli dependency disables `std`; this repo must retain its executed cross-target gate rather than treating that architecture as proof. [Source: no-std API](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/src/lib.rs#L1-L10), [Brotli dependency](https://github.com/nicoburns/wuff/blob/0775526a3555e089d2fce140f755cb225e35cdc7/wuff/Cargo.toml#L33-L41), [WOFF2 reconstruction rule](https://www.w3.org/TR/2024/REC-WOFF2-20240808/#table_dir_format)

**Arbitrary inputs and fit.** The API accepts arbitrary byte slices, but the renderer exposes it on this path only to qualified, digest-verified built-in WOFF2. It is the strongest reuse decision in the survey because all 230 official assets have already passed a local decode probe; arbitrary-font safety remains unproven and is outside the approved sealed-asset surface. [Source: approved built-in boundary](../renderer-spec-v1.md#831-semantic-demand-and-face-selection), [existing local qualification](font-subsetting-primary-sources.md#ttf2woff2-0132)

### `ttf2woff2 0.13.2`

**Interface and directions.** `encode`, `encode_no_transform`, and `encode_with_options` take sfnt bytes and produce WOFF2, with explicit Brotli quality, `glyf`/`loca` transform, and thread-count controls. It is packaging only: every source table is sorted and copied or transformed; there is no glyph/layout/name/variation selection. [Source: exports](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/lib.rs#L1-L17), [options](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L20-L61), [table assembly](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L146-L218)

Only sfnt flavor `0x00010000` is accepted, so CFF/OpenType and collections are rejected. Variable TrueType fonts can pass through because variation tables are ordinary copied tables, but the encoder does not interpret or validate their semantic consistency after subsetting. The restriction fits the current sealed corpus because all 230 `wuff` decodes had that TrueType flavor; it does not support arbitrary OpenType inputs. [Source: flavor check](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/sfnt.rs#L8-L39), [API contract](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L356-L383), [corpus evidence](font-subsetting-primary-sources.md#ttf2woff2-0132)

**Determinism and targets.** The default single-thread encoder is documented as fully deterministic. Multi-thread output depends on thread count; the WASM build ignores multi-thread requests and always uses the same single-thread branch. A renderer must freeze one quality, transform setting, and `threads = None`, and compare executed native/WASM bytes. [Source](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L20-L59), [compression branch](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L221-L260)

**Safety, build, and resources.** The crate and its normal dependency list are pure Rust, there is no package build script or `unsafe` in the inspected crate source, and the CLI can be excluded with `default-features = false`. It is not panic-free by contract: the source has an internal `unwrap`, and it allocates vectors from table counts and derived total lengths without `try_reserve` or a caller allocator/budget. The adapter must preflight conservative bounds or a fork must expose checked reservation and renderer resource hooks. [Source: manifest](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/Cargo.toml#L16-L33), [sfnt allocation](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/sfnt.rs#L21-L65), [encoding allocation and unwrap](https://github.com/0x6b/ttf2woff2/blob/8a9b82a00eb8af1e33af02706241c4b89106e01f/src/woff2/encoder.rs#L263-L328)

**Fit.** This is the preferred encoder for the sealed corpus, not a generic public font converter. Admission still requires all-230 generated-output browser acceptance, decode/parse validation, malformed-sfnt tests, memory preflight, and byte/resource-trace parity.

### `subsetter 0.2.6`

**Interface and scope.** The API subsets one sfnt/collection face from caller-supplied glyph IDs and a `GlyphRemapper`; a separate feature-gated call creates a static instance at variation coordinates. It supports TrueType and CFF, and the variation path converts CFF2 to TrueType. TrueType composite closure is performed, but the caller is responsible for the initial glyph set. [Source: public APIs](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/lib.rs#L101-L139), [flavor and composite handling](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/lib.rs#L142-L195)

**Why it is not a web-font candidate.** The maintainer explicitly states that output is for PDF and “most likely” unusable elsewhere. The implementation removes `cmap`, GDEF/GSUB/GPOS, OS/2, vertical-origin and other web-required/behavioral data, retaining a compact set of outlines, metrics, hinting, `name`, and `post`. It retains copyright names, but does not provide configurable name/language policy. It has no WOFF/WOFF2 codec. [Source: declared scope](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/README.md#L3-L28), [actual table selection](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/lib.rs#L209-L250)

**Determinism, safety, targets, and resources.** Output tables are sorted by tag before writing, so the implementation has a stable construction order, but upstream promises no cross-target byte contract. The crate denies unsafe and has no build script; default variable support adds pure-Rust fontations/kurbo dependencies. Reachable `expect`/`unwrap` sites and infallible vectors remain, and there is no caller resource-accounting API or upstream WASM gate. [Source: deterministic construction](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/lib.rs#L286-L349), [unsafe policy and manifest](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/lib.rs#L70-L87), [features](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/Cargo.toml#L28-L40), [representative panic sites](https://github.com/typst/subsetter/blob/c3f23c67bc0190587f639bda84dc0005ca3f54d5/src/remapper.rs#L79-L94)

**Arbitrary inputs and fit.** It accepts general sfnt bytes and returns structured errors for many malformed cases, but its deliberate PDF information loss is disqualifying regardless of safety qualification. Reusing it would require rebuilding precisely the hard web-font tables and closure policy that a general subsetter is supposed to provide.

### Allsorts `0.17.0`

**Interface and directions.** Allsorts parses OpenType, WOFF, and WOFF2 and exposes shaping, variable-font instancing, and a `subset(provider, glyph_ids, profile, cmap_target)` API. Its subset result is sfnt; it does not encode WOFF/WOFF2. The public subsetter requires `.notdef`, takes glyph IDs rather than text, and performs TrueType composite closure. [Source: advertised formats](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/README.md#features), [subset API](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L217-L253), [composite closure](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/tables/glyf/subset.rs#L24-L61)

**Web-font scope.** The README describes subsets as suitable for PDF embedding. `SubsetProfile::Minimal` retains the minimum standalone tables, and `CmapTarget::Unicode` exists because browsers reject a Mac-Roman-only cmap. However, there is no GSUB/GPOS glyph closure in the subset API; layout tags may be named in a custom profile, but the subset builders explicitly construct only cmap/outlines/metrics/names/OS/2/post/hinting tables. It is therefore not a general shaping-preserving web subsetter. [Source: profiles and browser cmap note](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L28-L121), [TrueType builder](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L255-L365), [CFF builder](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L440-L523)

The complete source `name` table is passed through when selected; there is no name-ID/language filtering. Separate instancing supports `gvar` TrueType and CFF2 and rewrites names, but that does not add layout closure to `subset`. [Source: name pass-through](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L332-L360), [instancing scope](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/variations.rs#L120-L166)

**Determinism, safety, build, resources, and WASM.** Output tables use a `BTreeMap` and checked serializers, which supports repeatability, but there is no byte-stability promise. The crate has no build script, but its parser contains explicit unsafe fast paths and its dependency graph includes `libc` and `ouroboros`. Default WOFF1 support selects the native zlib backend; a pure-Rust `flate2_rust` feature is available. CI covers native operating systems and Rust backends, not `wasm32-unknown-unknown`. Internal vectors allocate from font-derived counts and there is no renderer budget API. [Source: ordered builder](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/subset.rs#L188-L199), [unsafe reads](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/src/binary/read.rs#L96-L126), [manifest and backends](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/Cargo.toml#L20-L70), [CI matrix](https://github.com/yeslogic/allsorts/blob/efab0fc769287f4ced68bbd723c328c9d9b89698/.github/workflows/ci.yml#L14-L38)

**Arbitrary inputs and fit.** Allsorts is a credible maintained parser/shaper and PDF engine, but its unsafe/native-default graph and missing layout closure fail this repository's web-font and safety gates. It offers no advantage over the narrower `wuff` plus `skera` architecture.

## External capability references

### HarfBuzz `14.2.1` and `harfbuzzjs 1.4.0`

**Interface and font scope.** `libharfbuzz-subset` is the mature behavior benchmark. Its public API accepts Unicode/glyph sets; drop/no-subset table sets; retained name IDs/languages; layout features/scripts; flags for hinting, glyph IDs, CFF desubroutinization, names, unknown tables, layout/bidi closure and variation optimization; and axis pin/range operations. It supports TrueType, CFF/CFF2, layout and variable-font instancing, producing an sfnt face. It has no WOFF/WOFF2 codec. [Source: subset API and flags](https://github.com/harfbuzz/harfbuzz/blob/56feae4035bdd48f62ba2b8d8c16232d4d89b3a4/src/hb-subset.h#L35-L222), [axis APIs](https://github.com/harfbuzz/harfbuzz/blob/56feae4035bdd48f62ba2b8d8c16232d4d89b3a4/src/hb-subset.h#L224-L257)

Default policy retains name IDs 0 through 6 in US English, drops a documented group of legacy/layout/bitmap/SVG/Graphite tables, passes hint programs through, keeps all layout scripts, and retains a finite layout-feature list. A caller can override all of those sets. This breadth, plus current release fixes for subsetting crashes and 32-bit `gvar` overflow, makes HarfBuzz the primary differential oracle for closure and table behavior. [Source: current defaults](https://github.com/harfbuzz/harfbuzz/blob/56feae4035bdd48f62ba2b8d8c16232d4d89b3a4/src/hb-subset-input.cc#L32-L184), [14.2.1 release notes](https://github.com/harfbuzz/harfbuzz/releases/tag/14.2.1)

**Safety and resource fit.** HarfBuzz states that robustness precedes correctness and performance and participates in OSS-Fuzz, but its C++ API exposes success/failure, not a hard allocation/work budget or Rust panic-free contract. Native integration would require unsafe FFI and C/C++ compilation/linking, contrary to the default dependency and build-script policy. It is suitable for broad untrusted-font processing in its own ecosystem, but not proven against this renderer's deterministic semantic ledger. [Source: project priorities and fuzzing](https://github.com/harfbuzz/harfbuzz/blob/56feae4035bdd48f62ba2b8d8c16232d4d89b3a4/README.md#harfbuzz), [current repository gate](../renderer-spec-v1.md#10-dependencies-assets-and-distribution)

**`harfbuzzjs`.** The current subset artifact is compiled from the exact HarfBuzz 14.2.1 gitlink using Emscripten C++, `HB_TINY`, no exceptions/RTTI, a 65 MiB initial memory, and explicit re-enablement of CFF, layout, variation, style and vertical functionality. It is a low-level sfnt subset WASM module; it does not decode or encode WOFF2. [Source: build](https://github.com/harfbuzz/harfbuzzjs/blob/e55f3ce887a1a5437d8e7a3a3730123c7a49a5f6/Makefile#L1-L52), [configuration](https://github.com/harfbuzz/harfbuzzjs/blob/e55f3ce887a1a5437d8e7a3a3730123c7a49a5f6/config-override-subset.h), [gitlink](https://github.com/harfbuzz/harfbuzzjs/tree/e55f3ce887a1a5437d8e7a3a3730123c7a49a5f6/harfbuzz)

That artifact runs under a JavaScript/WebAssembly host; it is not a Rust crate compiled into `wasm32-unknown-unknown`, and native use would require either a second WASM runtime or native HarfBuzz. Its fixed initial memory and internal growth/allocation are not renderer semantic charges. It therefore fails both native/WASM deployment shape and resource-accounting gates even if repeated output proves deterministic. Excalidraw's older `harfbuzzjs 0.3.6` binding remains the exact compatibility reference described in the companion report, not the version recommended for new generic integration. [Source: current package shape](https://github.com/harfbuzz/harfbuzzjs/blob/e55f3ce887a1a5437d8e7a3a3730123c7a49a5f6/package.json), [current repository production gate](../renderer-spec-v1.md#10-dependencies-assets-and-distribution), [pinned Excalidraw identity](font-subsetting-primary-sources.md#source-identities)

### `subset-font 2.5.0`

This Node package demonstrates the closest off-the-shelf end-to-end API: `subsetFont(buffer, text, options)` accepts sfnt/WOFF/WOFF2, runs HarfBuzz layout closure, can retain extra name IDs or restrict variation axes, and emits sfnt, WOFF, or WOFF2. It uses `fontverter` for both WOFF directions because HarfBuzz itself is sfnt-only. [Source: API](https://github.com/papandreou/subset-font/blob/74ee885bc50c862b0a238e4dc32a74e2719cfe71/README.md#L42-L65), [implementation](https://github.com/papandreou/subset-font/blob/74ee885bc50c862b0a238e4dc32a74e2719cfe71/index.js#L23-L184)

It also shows why this functionality is not “generic SVG integration”: the caller supplies one text string and all font bytes/options; it neither inspects SVG nor writes CSS. Operationally it reads a packaged WASM file through Node `fs`, uses JavaScript buffers and a global one-at-a-time limiter, and declares broad semver dependency ranges without a published lockfile. It exposes no allocation/work budget and no cross-target byte guarantee. It is a useful behavioral prototype and test oracle, but fails the pure-Rust, no-production-JS, native, WASM, deterministic-graph, and bounded-allocation gates. [Source: loading and serialization](https://github.com/papandreou/subset-font/blob/74ee885bc50c862b0a238e4dc32a74e2719cfe71/index.js#L1-L15), [limiter](https://github.com/papandreou/subset-font/blob/74ee885bc50c862b0a238e4dc32a74e2719cfe71/index.js#L184-L188), [dependency ranges](https://github.com/papandreou/subset-font/blob/74ee885bc50c862b0a238e4dc32a74e2719cfe71/package.json)

### fontTools `4.63.0`

`fonttools subset` is the mature generic web-font benchmark. It accepts TrueType/CFF sfnt and WOFF input, supports text/Unicode/glyph selection, layout closure and feature/script filtering, hinting, CFF subroutines, table drop/pass-through policy, configurable name IDs/languages, glyph names, and deterministic options such as disabling timestamp recalculation. It can directly emit WOFF or WOFF2 and describes its optimizations as aimed at web fonts. [Source: official subset documentation](https://fonttools.readthedocs.io/en/latest/subset/index.html), [pinned implementation and CLI contract](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/Lib/fontTools/subset/__init__.py#L29-L244)

Its WOFF2 reader/writer supports CFF- and TrueType-flavored fonts, transforms `glyf`/`loca` and optionally `hmtx`, sorts tables, drops DSIG, and uses Brotli. The default `--no-recalc-timestamp` supports deterministic runs, but optional uharfbuzz repacking and exact Python/Brotli versions must be frozen to make bytes reproducible. [Source: WOFF2 API](https://fonttools.readthedocs.io/en/latest/ttLib/woff2.html), [pinned WOFF2 writer](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/Lib/fontTools/ttLib/woff2.py#L142-L284), [timestamp/repacker options](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/Lib/fontTools/subset/__init__.py#L119-L136)

It cannot be linked into this renderer: it requires Python, WOFF2 requires the Brotli Python extension, installation can compile optional Cython/C extensions, and neither Python nor those native extensions are the repository's `wasm32-unknown-unknown` production model. Python containers and parser operations expose no renderer allocation/work-accounting hook, and the source uses assertions/exceptions rather than a panic-free Rust surface. It remains the best external differential oracle and offline corpus-analysis tool. [Source: WOFF extras and optional extensions](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/setup.py#L38-L124), [Python/runtime package declaration](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/setup.py#L339-L376)

The `SVG` mentioned by fontTools is the OpenType `SVG ` glyph table, not an SVG document export pipeline. `--pretty-svg` only formats that font table while subsetting. [Source](https://github.com/fonttools/fonttools/blob/978d9edccb60ea0e5fbad7015cb11817c3532328/Lib/fontTools/subset/__init__.py#L221-L224)

### fontkit `2.0.4`

fontkit parses and shapes sfnt, WOFF and WOFF2 in Node/browser JavaScript, but its subset object is glyph-ID driven and always starts with `.notdef`. The TrueType encoder includes composite children and emits only the PDF-required `head`, `hhea`, `loca`, `maxp`, hint, `glyf`, and `hmtx` tables; its own comments list standalone `name`, `cmap`, OS/2 and `post` as additional, but the code does not emit them. CFF output is similarly outline-focused. [Source: subset base](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/src/subset/Subset.js), [TrueType subset](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/src/subset/TTFSubset.js#L13-L130), [CFF subset](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/src/subset/CFFSubset.js#L16-L170)

It performs no semantic Unicode/layout closure and emits no WOFF2 subset; WOFF2 is an input parser. It has no name/variation/table-retention policy suitable for web output, no resource budget, no Rust/native interface, and no maintenance signal after 2024-08. It is neither a production candidate nor a stronger oracle than HarfBuzz/fontTools. [Source: format registration](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/src/index.js), [subset dispatch](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/src/TTFFont.js#L425-L435), [package manifest](https://github.com/foliojs/fontkit/blob/fbf3b9ef21eebd219eb73e666faed573af0fba09/package.json)

### Google WOFF2 current master

Google's C++ reference library provides bidirectional sfnt/WOFF2 conversion and remains actively hardened, including a 2026 malformed-`glyf` overflow fix. It does not subset fonts. The build requires a C++ compiler and Brotli encoder/decoder libraries, and a Rust integration would add FFI, native linking/build provenance, and an independently metered allocator surface. It is appropriate as a conformance oracle, not as a production dependency under this repository's gates. [Source: current fix](https://github.com/google/woff2/commit/fb9c3379f2605b10f3e8f1d9636664ab5576775c), [build and directions](https://github.com/google/woff2/blob/fb9c3379f2605b10f3e8f1d9636664ab5576775c/README.md), [CMake native dependencies](https://github.com/google/woff2/blob/fb9c3379f2605b10f3e8f1d9636664ab5576775c/CMakeLists.txt#L18-L92)

The older Rust `woff2 0.3.0`, `woff2-patched 0.4.0`, and `woff2-sys 0.0.1` packages do not improve the choice: the first two are decode-only and have weaker maintenance than `wuff`; `woff2-sys` is a 2017 C++ FFI package. [Source: `woff2` history](https://crates.io/api/v1/crates/woff2), [`woff2-patched` history](https://crates.io/api/v1/crates/woff2-patched), [`woff2-sys` history](https://crates.io/api/v1/crates/woff2-sys)

## SVG font integration

### What a reusable integration module would have to do

A genuine integration package for this renderer would need to identify semantic text before serialization; resolve the renderer's family substitutions and Unicode-range faces; collect Unicode scalar values in deterministic scene order; choose and subset exact built-in assets; emit ordered `@font-face` rules and data URLs; and account for every intermediate and output byte. Parsing generic XML or seeing final shaped glyph IDs is not equivalent, because Excalidraw compatibility depends on source scene semantics, original text, family/chunk policy, and declaration ordering. Those semantics are documented in the companion report. [Source: pinned collection/selection behavior](font-subsetting-primary-sources.md#collection-and-face-selection), [ordering and SVG scope](font-subsetting-primary-sources.md#ordering-and-svg-scope)

### `usvg` / resvg

`usvg 0.47.0` is the strongest generic Rust SVG text layer surveyed. With `text`, it parses and resolves text into chunks and non-overlapping spans; public APIs expose chunk text, family/style/stretch/weight/variation properties, and positioned glyphs. It can therefore assist analysis of an already supplied generic SVG. [Source: current text properties](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/tree/text.rs#L115-L178), [chunks/spans](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/tree/text.rs#L319-L576)

It does not perform font subsetting. Its text feature uses `fontdb`, rustybuzz and `ttf-parser`; default features also load system/fontconfig and mmap fonts, while this repository correctly disables defaults and supplies its own assets. [Source: current features](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/Cargo.toml#L37-L62), [workspace pin/features](../../Cargo.toml#L38-L54)

It also does not emit embedded web fonts. `Text::flattened` converts laid-out glyphs to paths/groups/images, and `Tree::to_string` either writes those flattened graphics or, with `preserve_text`, writes text/font attributes. The writer's `defs` pass emits paint servers, paths and filters, not a generated style block or `@font-face`; the pinned source contains no `font-face` handling. [Source: flattening](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/text/flatten.rs#L45-L165), [writer options](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/writer.rs#L17-L125), [defs writer](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/writer.rs#L366-L463)

For direct Excalidraw export, walking a `usvg` tree would be the wrong seam: it would discard the richer typed scene plan and make serialization/parser behavior part of the compatibility path. For sanitized nested SVG input, `usvg` remains appropriate for rendering, but nested image-font collection is outside the approved direct-export subsetting scope. [Source: current typed-plan prohibition](../renderer-spec-v1.md#9-architecture), [approved scope](font-subsetting-primary-sources.md#decision-summary)

### Generic SVG serializers and text-to-path tools

The Rust `svg 0.18.0` package describes itself as an SVG composer and parser; its interface manipulates document nodes and raw text. It has no font resolution, shaping, subsetting, WOFF2, or CSS font-generation layer. Its 2024 release is established but adds no semantic capability useful here. [Source: package metadata](https://crates.io/api/v1/crates/svg/0.18.0), [pinned crate source](https://docs.rs/crate/svg/0.18.0/source/src/lib.rs)

Text-to-path facilities, including `usvg`'s own flattener, solve a different problem: they remove live font dependencies by serializing glyph geometry. They do not preserve selectable/searchable text and cannot emit a smaller live-font SVG. Likewise, font database packages resolve faces but do not know scene-level compatibility families, source text, Unicode-range chunks, CSS order, or output policy. [Source: `usvg` flattened contract](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/tree/text.rs#L579-L606), [font resolver/database role](https://github.com/linebender/resvg/blob/3a0fdba53ccf2d346b54cc53ba7adf0ee60d0707/crates/usvg/src/parser/options.rs#L79-L101)

### Result

No surveyed Rust, C/WASM, Python, or JavaScript package gathers the required Excalidraw semantic usage and emits subset `@font-face` declarations. `subset-font` supplies font-bytes-plus-text subsetting but no SVG semantics/CSS; `usvg` supplies resolved SVG text but no subsetting/CSS; fontTools' SVG support concerns a table inside a font; and fontkit's subset output is PDF-minimal. Composing any two still leaves the compatibility policy, resource model, deterministic order, naming/licensing, and artifact validation repository-owned.

## Repository-owned remainder

Even after reusing three narrow font packages inside the two approved deep modules, the repository must own these compatibility-critical responsibilities:

- **Semantic collection:** walk the typed scene, apply the approved participation/omission rules, collect compatibility-normalized `originalText` plus every emitted generated label, and resolve family substitutions and the exact CJK copied-set rule before any font library call.
- **Face selection and order:** intersect family scalar sets with the sealed catalog's Unicode ranges, preserve catalog/fallback/declaration order, deduplicate semantically, and choose exact digest-verified source assets.
- **Frozen subset profile:** explicitly set Unicode/glyph inputs, layout scripts/features, closure flags, hinting, table drop/pass-through sets, name IDs/languages, legal records, glyph-ID policy, variation policy, and unknown-table behavior. Dependency defaults cannot define a compatibility revision.
- **Resource control:** preflight conservative maximum allocations before each dependency call; charge canonical scalar, candidate-face/range consideration, selected-face, decode, plan, sfnt, encode, validation, CSS/base64 and output events; release at fixed phase boundaries; and make cache hits replay identical semantic charges.
- **Panic and malformed-data boundary:** remove or contain reachable dependency panics, use checked reservation in any controlled fork, reject unsupported sfnt/table combinations deterministically, and never return a partial artifact.
- **WOFF2 profile:** freeze exact decoder/encoder versions and features, Brotli quality, transform choices, single-thread mode, table ordering, output validation and cross-target byte expectations.
- **SVG/CSS emission:** generate one deterministic style block, quote/escape names, serialize media type and base64 without environmental variation, and preserve declared family/fallback behavior. No surveyed SVG library supplies this layer.
- **Licensing and names:** enforce the approved Modified Version and Reserved Font Name aliases, matching OpenType/CSS identities, retained copyright/license records, complete license texts, and per-subset notice policy. A subsetter's defaults cannot replace that policy.
- **Qualification:** all 230 assets and selected-codepoint classes; native and executed browser-WASM bytes/resource traces; malformed/fuzz inputs; source-versus-subset shaping; browser and Rust-viewer rendering; legal records; and material post-base64 size reduction.

These are not glue that should be delegated to a “generic SVG” package. They are the stable module boundary: dependencies transform one verified font at a time, while the renderer owns why, when, in what order, under what budget, and with what observable bytes that transformation occurs.

## Final recommendation

Reuse and qualify `wuff 0.2.8` + `skera 0.5.1` + `ttf2woff2 0.13.2` behind the package-private `font_subset` module, choosing a controlled fork wherever the adapter cannot satisfy the fixed safety, resource, semantic, or deterministic-byte gates. Keep HarfBuzz and fontTools outside production as differential oracles. Build the Excalidraw adapter and `svg_fonts` integration in the renderer because no reusable SVG semantic-integration package was found, and retain both deep modules there until a concrete extraction need appears. This recommendation does not admit any package to production; the complete qualification and release evidence remains pending.
